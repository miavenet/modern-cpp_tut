# Lesson 03 — Measuring Latency Honestly, Kernel Bypass, and Branch Hints

Time: about 43 minutes (18 minutes reading, 4 minutes of runs, 11 cards). Two sittings is fine.

**The hook.** A latency test reports a 99.9th percentile of 0.5 ms. The same
server, the same stall, measured a second way, reports 995 ms. Both numbers
come from one 40-line program in this lesson. Only one of them describes what
your customers saw.

**You will be able to:** spot coordinated omission, read a tick counter

## Pretest — guess first

### Card M6-P3 · Pretest
Q: A test client sends one request, waits for the reply, then sends the next
   (a "closed loop"). The server freezes for one second in the middle of the
   test. Guess: in the client's results, how many requests show the freeze,
   and why does that make the tail percentiles look too good?
<details><summary>Answer</summary>
Key:
  - Only one request (the one in flight) records the freeze, because the client
    stopped sending while it waited. A real feed keeps arriving during the
    freeze, so about a second's worth of requests would have been delayed.
  - The test silently omits all those slow samples. This is called coordinated
    omission: the measuring tool coordinates with the stall and leaves it out.
</details>

### CONCEPT C6  Coordinated omission, and reading a clock correctly

A load generator that waits for each reply stops sending during a stall. Its
histogram then omits requests that would have arrived independently. Predict
how the two clients below will report the same one-second pause.

**Coordinated omission, simulated.** `modules/06-hft-patterns/lab/measure/coordinated_omission.cpp`
simulates a server that needs 0.5 ms per request, except for one 1-second
stall at t = 5 s, over 10 seconds. A *closed-loop* client sends, waits, then
sends again. An *open-loop* client sends a request every 1 ms no matter what,
as a market feed does.

```sh
clang++ -std=c++20 -O2 modules/06-hft-patterns/lab/measure/coordinated_omission.cpp \
  -o "${TMPDIR:-/tmp}/co" && "${TMPDIR:-/tmp}/co"
```

```
closed-loop  n= 9000  p50=    0.5  p99=    0.5  p99.9=    0.5  max= 1000.5 ms
open-loop    n=10000  p50=    0.5  p99=  950.5  p99.9=  995.5  max= 1000.5 ms
```

The closed loop lost 1000 samples (it was waiting) and its p99.9 hides the
stall. The open loop records every request that queued behind the stall.

**Reading a clock.** The portable clock is `std::chrono::steady_clock`
(C++11): it never goes backwards. CPUs also have tick counters that can be
read without a system call:

```cpp
#if defined(__x86_64__)          // x86-64: time-stamp counter
    _mm_lfence(); t = __rdtsc(); _mm_lfence();
#elif defined(__aarch64__)       // arm64: generic timer, virtual count
    asm volatile("isb\n\tmrs %0, cntvct_el0" : "=r"(t) :: "memory");
#endif
```

Why the fence? A CPU may execute instructions out of order. Intel's manual
entry for RDTSC says it "is not a serializing instruction" and that software
"can execute LFENCE immediately before RDTSC" to wait for earlier
instructions (and LFENCE immediately after RDTSC keeps later instructions
from starting early). On arm64, the Linux kernel reads `cntvct_el0` right after an
`isb` (instruction synchronization barrier) for the same reason. Without the
fence, the counter can be read before the code you meant to time has finished.
These fences address CPU execution ordering. Also verify compiler placement;
measuring global store visibility requires additional ordering.

**See it yourself** (`lab/measure/ticks.cpp`, arm64 part tested; the x86-64
part was compile-checked only). On the test Mac it printed
`counter frequency: 24000000 ticks/s`: one tick is about 41.7 ns, so this
counter cannot time a 10 ns block directly. Time many repetitions instead.

**Hardware timestamps.** A software timestamp at the start of your handler
measures when *your code* started. Network cards that support it can stamp
each packet when it arrives; Linux exposes this as `SOF_TIMESTAMPING_RX_HARDWARE`
("timestamps generated by the network adapter"), while
`SOF_TIMESTAMPING_RX_SOFTWARE` is taken after the driver hands the packet to
the kernel. The gap between them is time your handler never sees.

**Rule:** drive tests open-loop, report the tail, fence your tick reads, and
start the clock where the packet starts.

| report | what it retains | useful for | wrong-choice smell |
|---|---|---|---|
| average | total divided by count; hides rare stalls | total work or broad trend | a clean mean beside user complaints |
| p99 or p99.9 | a chosen tail threshold; misses rarer events | a stated service target | no sample count or arrival model |
| maximum | worst observed sample; sensitive to run length | investigating outliers | treated as a stable forecast |

Report the percentile tied to the deadline, the maximum and the sample count;
a good-looking tail from a closed-loop sender is the warning sign.

### Card M6-J3 · Apply
Q: An AI assistant wrote this open-loop C++20 test, which records each
   request's scheduled send time, and says it "proves our p99.99 is under
   2 ms". The function stands in for a non-blocking send; replies are timed
   against `scheduled` elsewhere. Is the test right here? What would you check
   first, and what would change your verdict? Answer format: three short sentences.
   ```cpp
   #include <chrono>
   #include <thread>
   #include <vector>
   void send_request() {}
   int main() {
       using namespace std::chrono;
       std::vector<steady_clock::time_point> scheduled;
       auto next = steady_clock::now();
       for (int i = 0; i < 1000; ++i) {      // one request every 1 ms
           scheduled.push_back(next);
           send_request();
           next += 1ms;
           std::this_thread::sleep_until(next);
       }
   }
   ```
<details><summary>Answer</summary>
Key:
  - The arrival model is right, but 1,000 requests cannot support a p99.99 claim: only 0.1 of them is expected beyond that percentile, so the reported value is essentially the slowest sample of this run.
  - At p99.99, 10,000 samples give only one expected exceedance. A useful tail estimate needs substantially more observations and an uncertainty statement. Collect representative traffic over a longer period, report the maximum and sample count, and distinguish this run’s percentile from a production guarantee.
</details>

### Card M6-Q5 · Recall

   In one or two sentences: what time does that stamp miss, and what kind of
   timestamp captures it?
   Answer format: one line.

<details><summary>Answer</summary>
Key:

### Card M6-G5 · Spot the trap
Q: You read the x86-64 time-stamp counter with plain `__rdtsc()` before and
   after a short block, and the results are erratic. (a) In one sentence, why
   can the counter read land in the wrong place? (b) What do you add on x86-64,
   and what is the arm64 counterpart used before reading `cntvct_el0`?
   Answer format: one line; separate labeled parts with semicolons.

<details><summary>Answer</summary>
Key:
  - (a) The CPU executes instructions out of order and RDTSC is not a
    serializing instruction, so the counter can be read before the earlier
    instructions you meant to time have finished.

    instructions out). arm64: `isb` before `mrs ..., cntvct_el0`.
</details>

### CONCEPT C11  Measuring tails on a Mac: the course histogram

The course's measured labs (module 01 lesson 05, 03 lesson 05, 04 lesson 05,
05 lesson 06, 07 lesson 05, and this module's lesson 05) all print their
results with one header, `lab/measure/lat_hist.hpp`. Three rules decide
whether what it prints means anything.

**Predict first:** `lab/measure/clock_tail.cpp` times *nothing* (an empty interval) 1,000,000 times. Before reading on, guess its p50 and its max. Commit to two numbers.

<details><summary>Output</summary>

p50 = 0 ns and p99 = 42 ns: the clock only moves in 42 ns ticks, so an empty interval reads 0 or one tick. The max was about 19 µs: the OS interrupting the program, not the code. Rules 2 and 3 below explain both.

</details>

**1. A percentile needs samples beyond it.** p99.99 is decided by the slowest
0.01% of samples. With 10,000 samples that is *one* sample, so "p99.99" is
just this run's slowest call. The header asks for at least 10 samples beyond
the rank: n ≥ 10 / (1 − q). p99 needs 1,000, p99.9 needs 10,000, p99.99 needs
100,000. Below that it prints `n/a` instead of a number.

**2. The clock has a floor.** On this Mac `steady_clock` moves in steps of
the 24 MHz system counter: about 41.7 ns. Timing *nothing* 1,000,000 times
(`lab/measure/clock_tail.cpp`, 7 runs) gave p50 = 0, p99 = 42, p99.99 = 85
[85–167] ns. Anything shorter than a tick reads as 0 or 42. So time a *batch*
of operations per sample (the module 05 lab used 16 `push_back`s), and read
the result as batch latency. Do not trust a reported resolution: here `steady_clock::period`
says 1 ns and `clock_getres(CLOCK_MONOTONIC)` says 1000 ns (`CLOCK_UPTIME_RAW` says 42 ns), yet the smallest non-zero step
between two reads is 41 ns. Measure the step. The header prints the floor next to every
histogram.

**3. The median cannot see a rare cost, and a short run cannot see the OS.**
The same empty interval had a max of 19 µs [14–30 µs] over 1,000,000 samples:
interrupts and the scheduler taking the core away. A 5,000-sample run of the
same code showed a max of 84 ns and looked perfect. A rare cost that hits a
fraction *f* of samples shows only above percentile 1 − *f* (module 05
lesson 06), so you need enough samples to reach it, and a median never will.

**What macOS will not let you control,** so label every number with it: no
core pinning (affinity is only a hint); low-priority (background QoS) threads
are steered toward the two efficiency cores (we saw the effect, a 3x slower
median, in module 03 lesson 05, but cannot observe the placement); no isolated cores; and a Time Machine backup can
saturate the disk (check `tmutil currentphase` first). The course labs report
the machine, compiler, flags, sample count and "shared machine" on every run,
repeat 5 to 7 times, and show the median with the lowest and highest. Trust
ratios and counters over nanoseconds.

**Rule:** at least 10 samples beyond the percentile, batches above the clock
floor, the machine named, and the spread shown; otherwise the tail number is
noise.

### Card M6-LPA2 · Fix it
Q: You want the latency distribution of a function that takes about 8 ns, on a
   machine whose clock ticks every 42 ns (the floor `clock_tail.cpp` printed
   on this course's Mac; run it on yours and use your own number in real life).
   Each sample should span at least 10 ticks, so calls per batch =
   ceil(10 x tick / call time).
   Worked first, for a 12 ns call: 10 x 42 = 420 ns; 420 / 12 = 35 exactly; so 35 calls.
   Now finish yours (8 ns): 10 x 42 = 420 ns; 420 / 8 = ___; calls per batch = ___.
   Answer format: one whole number, the calls per batch (the second blank).

<details><summary>Answer</summary>
Key:
  - 53. Ten ticks are 10 x 42 = 420 ns; 420 / 8 = 52.5, and you round *up*,
    so 53 calls per batch (52 calls would span only 416 ns, under ten ticks).
    Each sample is then batch latency: a rare slow call shows as one slow
    batch, and you divide by 53 only for a per-call *mean*, never for a tail.
</details>

### Card M6-LPA3 · Apply
Q: A colleague's load test of a REST pricing service collected 2,000 requests
   and reports "p50 = 3 ms, p99.99 = 4 ms, so the tail is flat". Give two
   reasons this does not show a flat tail.
   Answer format: one line; separate the two reasons with a semicolon.

<details><summary>Answer</summary>
Key:
  - Too few samples: p99.99 needs about 100,000 under the course rule; with
    2,000 there is not even one sample beyond the p99.99 rank, so the number

</details>

### CONCEPT C7  Kernel bypass and polling (Linux, untested here)

**Why poll at all?** Interrupts and a kernel wake-up do useful work, but they
also add a hand-off before the application sees the packet. DPDK's poll-mode
driver chooses to spend a core watching a receive ring instead.

This section describes Linux and DPDK mechanisms; the runnable labs target macOS.

**A typical interrupt-driven path.** A packet arrives; the card signals an *interrupt*; the
kernel runs its network stack; your thread, perhaps asleep in `recv`, is
woken and copies the data out with a system call.

**Bypass.** DPDK's poll-mode drivers are "designed to work without
asynchronous, interrupt-based signaling mechanisms": a dedicated core runs a
tight loop, *polling* receive rings in memory for new packets. The card writes
packets into memory buffers (DMA) that the application can read directly.

**Related Linux tools, not the same thing.**
- AF_XDP sockets: the kernel "will first try to use zero-copy", falling back
  to copy mode when the driver does not support zero-copy.
- `io_uring` is "a Linux-specific API for asynchronous I/O" built on rings
  shared with the kernel. Requests are still processed by the kernel, so it is
  not kernel bypass.

**NUMA.** A server with two CPU sockets has memory and devices attached to
each socket (non-uniform memory access). Place the polling core, packet-buffer
pool and NIC on the same NUMA node where possible. Check the pool's creation
settings: its placement is chosen at allocation, not by the thread that later
polls it. From the outside, several problems look alike: a thread on the wrong
socket, other work sharing the polling core, or a slow test client. Change one
thing at a time and measure again.

**Rule:** a DPDK receive loop spends a polling core to avoid the usual
interrupt-driven kernel receive path; place the core and buffers near the
card and measure.

| wait style | cost | guarantee | right when / wrong-choice smell |
|---|---|---|---|
| busy-poll | consumes a core while idle | checks ring repeatedly | tight latency target; idle CPU saturation needs a reason |
| yield | asks scheduler to run other work | no fixed wake-up time | mixed work; missed tail target is the smell |
| block | scheduler may sleep the thread | avoids idle spinning | throughput or power matters; wake-up tail is the smell |

Pick the wait style from the latency budget and idle-core budget together;
an unexplained 100% polling core is a design review trigger.

### CONCEPT C8  Branch hints: `[[likely]]`, `[[unlikely]]`, and profile data

**Why the compiler needs a clue.** Source order alone cannot tell a compiler
which branch is common under your real traffic. A hint supplies a guess;
profile data supplies observed frequencies from a particular run.

**The idea.** In compiled code, one side of an `if` *falls through* (runs
straight on) and the other is a jump. A source `if` is not always a branch:
a compiler can turn a short one into a conditional select (`csel` on arm64,
`cmov` on x86-64), so count the conditional branches in the listing first.
C++20 added `[[likely]]` and
`[[unlikely]]`; the standard says they are "intended to allow implementations
to optimize" and notes that excessive use "is liable to result in performance
degradation". The C++98-era equivalent was the GCC extension
`__builtin_expect`.

**See it yourself** (`lab/measure/branch_hint.cpp`, assembly, Apple clang 21,
`-O2`, arm64):

```cpp
int handle(int px, bool halted) {
    if (halted) [[unlikely]] { on_halt(); return 0; }   // without HINT: no attribute
    return price_fast(px);
}
```

```
no hint:                         with [[unlikely]]:
  cbz  w1, LBB0_2                  cbnz w1, LBB0_2
  ...  call on_halt  (falls in)    b    price_fast   (common path falls in)
LBB0_2: b price_fast             LBB0_2: ... call on_halt
```

**Profile-guided optimisation (PGO).** Instead of guessing, build an
instrumented binary, run it on representative input, and rebuild with the
recorded counts. `lab/measure/pgo.cpp` has the exact commands
(`-fprofile-instr-generate`, `llvm-profdata merge`,
`-fprofile-instr-use`; clang's spelling, GCC uses `-fprofile-generate` /
`-fprofile-use`). On the test Mac the profile alone, with no
attribute, produced the same layout as `[[unlikely]]`. A profile is only as
good as its input: an unrepresentative or stale profile can steer the
compiler wrong.

**The trap.** A hint is your guess about production traffic. If the guess is
wrong, or traffic changes, you have moved the common path out of the
fall-through position and no warning tells you.

**Rule:** prefer measured profiles; use a hint only where you know the
frequency, and check the assembly to see whether it changed anything.

### Card M6-G7 · Spot the trap
